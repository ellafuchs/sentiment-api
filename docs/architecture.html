what they leave out

The model is one line of config. Everything below is the machinery that decides whether that line is allowed to change production.

1 · the path a change takes

A model swap is a pull request

There is exactly one way for a different model to reach users, and it starts as a diff a human can read.

The config carries two independent axes and the rules that judge them. model.* is what runs; runtime.* is how it executes; gate.* is what it has to beat.

model: source: hf id: distilbert-base-uncased-finetuned-sst-2-english revision: 714eb0fa89d2… # full 40-char commit SHA, validated runtime: kind: pytorch # onnx is a new class, not a refactor gate: min_accuracy: 0.88 min_macro_f1: 0.87 max_p95_latency_ms: 300 max_accuracy_regression: 0.02 # vs the model currently deployed

Merging is a human act, and the deploy is a second one. Branch protection is deliberately off — a solo project where the gate is advisory-by-policy teaches more than one where GitHub enforces it, and the enforcement is one setting away when it needs to be real. A push to main ships nothing; make ship triggers the pipeline, and make drift answers the question that separation creates — what is live, versus what you have committed.

2 · the release

Deploying is not releasing

Those are two decisions, so they are two commands. A new revision exists on real hardware, reachable, warmed and tested, while every user is still being answered by the old one.

The candidate gets its own hostname — candidate---sentiment-….run.app — so it can be driven over HTTP by the deploy tests before it is allowed near a user. Both questions the three scripts need answered, which revision is serving and where is the candidate, are asked in exactly one place: infra/lib.sh. The first attempt wrote that query three times, one copy was wrong, and the pipeline failed in CI on a query that had never been run locally.

what the canary compares

Error rate and p95, candidate against the incumbent, measured from the same place at the same moment. The incumbent is timed at 100% before the split, so the two numbers share the same network and the distance cancels.

what it cannot see

Accuracy. Sixty seconds of synthetic probes cannot detect a model that is quietly wrong — only the gate can, before the deploy, by comparing to the scores production reports. That is the whole reason the next picture exists.

Rollback is a traffic change, not a rebuild: the previous revision stays built and configured. Measured at 22 s to a cold target, 4 s to a warm one.

3 · the artifact

The image carries its own report card

One image is built per commit, tagged with the git SHA — never latest, because rollback has to be able to name an exact revision and latest makes "which image was that?" a question with no answer.

Weights are baked in at build time, so the same git SHA produces the same behaviour forever and there is no Hub outage at cold start. The build then scores that exact image over a 200-example golden set and layers the report back into it as a final stage — which is what lets the running service answer /metadata with the scores it was measured at.

That answer is a baseline for the next candidate. An unevaluated production image would make the regression check skip silently, and "no baseline" and "beat the baseline" produce the same green tick while being very different claims.

Cloud Run runs amd64; the laptop is arm64. Every image that ships is built --platform linux/amd64, which the container tests catch when it isn't.

4 · the gate

Two jobs, because they fail differently

ci.yml splits into check — lint, unit and contract tests, seconds, no model download — and gate, which builds the image, drives it over HTTP, scores it, and only then does the part that matters: fetches the live model's scores from production and compares.

0.885 clears a floor of 0.88 and is still a regression against the 0.900 already serving users. Ship three of those and every individual change was acceptable while the model got visibly worse.

So the floors are necessary and not sufficient: the highlighted row is the relative check, and it is the one that catches slow decay. The verdict goes in the pull request rather than the logs, because a gate nobody reads is not a gate.

Who is allowed to do what

No keys, and less permission than the plan asked for

CI / CD auth
Workload Identity Federation — GitHub presents a short-lived OIDC token, scoped to this repository. There is no service-account JSON anywhere to leak.
Deploy identity
Can build, push and deploy revisions, and can shift traffic. Deliberately cannot call run.services.setIamPolicy.
Making it public
The allUsers invoker binding is on the service, not a revision, so it lives in setup.sh where a human runs it. Granting CI that permission would let the deploy identity publish a private service to the internet.
Runtime identity
A dedicated service account whose only granted role is logging.logWriter. The container reaches nothing else.
Consequence
A fresh project needs setup.sh run twice — once before the service exists, once after — and nothing tells you so until a candidate returns 403.
What this architecture does not check

The honest list

Written down so they stay known gaps rather than assumptions.

Drift after deploy
The largest gap. A green gate cannot see accuracy rotting as real inputs drift away from the golden set. Nothing here watches production quality over time.
Real traffic
There are no users, so the canary measures its own synthetic probes. It is a rehearsal of the mechanism, not validation on real load.
Shadow deploys
No path for a candidate to see a copy of live traffic, logged and compared but not served.
Fail-open defaults
An empty environment falls back to the production project. An unset PROJECT should refuse to deploy, not deploy to prod.
Terraform
Infrastructure is a shell script mirroring the commands actually typed. Honest and readable, but not the real tool.
Model registry
No MLflow-style artifact, metric and lineage store. Git SHAs and baked reports do the job at this scale.

What is built — immutable artifacts tagged by commit, a gate before deploy, a canary, one-command rollback, model version as reviewable config — is the real production shape. What changes at a larger company is the number of tools plugged into each box, not the boxes.
