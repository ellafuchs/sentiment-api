Why it exists

When a normal service breaks, it throws an error. When a model breaks, it returns 200 OK with 99% confidence and is simply wrong.

Nothing to alert on. Nothing in the logs. No stack trace, no 500, no latency spike. The only thing that catches it is a test that already knows the right answer.

So the project is built around one idea: which model runs is a line in a config file, and changing that line is tested, gated, and reversible.

The example left in on purpose

"I would not recommend this to a friend." → POSITIVE 0.99

That's wrong, and the failing test is still in the suite. Deleting the test to get a green tick would hide a real weakness — which is exactly the failure mode the whole pipeline exists to catch.

Any step can say no. A bad version caught at smoke was seen by nobody. Caught at canary, by a tenth of callers for sixty seconds — and traffic returns automatically.

The old version stays built and configured the whole time. That's why going back is a traffic switch, not a rebuild.

Three things that went wrong

These are the parts worth telling. Each was invisible to a green test suite.

01 · the endpoint that never worked

119 tests passed. It was unreachable.

A /healthz health check. Every unit test passed, every container test passed. Then one test talked to the actually deployed service and got a 404.

Google's edge intercepts that exact path on Cloud Run — the request never reaches the container at all. The giveaway was in the headers:

/readyz 200 server: Google Frontend x-cloud-trace-context: 3a6c… /nonexistent 404 server: Google Frontend x-cloud-trace-context: 90a9… /healthz 404 (no server header, no trace id)

A path that doesn't exist gets a proper 404 from the app. /healthz never arrives. Renamed to /livez, with a test pinning /healthz at 404 — because the instinct on reading /livez is to "correct" it back.

02 · the canary that measured the atlantic

It rolled back a healthy version

The canary compared latency to a 300 ms limit and refused the deploy at 337 ms. The version was fine — probed directly minutes later it answered in 125 ms, ten times out of ten.

The limit was measured on a laptop in Israel. The canary ran on a GitHub server in the United States. Most of that 337 ms was the ocean.

Same two versions, minutes apart. The absolute numbers move by 2.4×. The difference between them barely moves. Only one of those is a property of the software.

Look at the second column's lower bar: 334 ms is the version already serving production, happily, for hours. The old check would have rejected a candidate for being indistinguishable from what was already live — while reporting the incumbent's own latency as a violation.

So the canary stopped using a fixed number. It now measures both versions from the same place at the same moment, and asks only whether the new one is worse. Distance and network cost sit in both numbers and cancel.

03 · why passing isn't enough

0.885 clears the bar and is still a regression

The minimum accuracy is 0.88. A model scoring 0.885 passes — while being worse than the 0.900 already serving users. Ship three of those and every individual change was "acceptable" and the model is now visibly worse. Nobody did anything wrong; the limit just never noticed.

So the deployed container carries its own report card, and every candidate is checked against what is actually live:

Known gaps

Deliberate omissions, listed so they stay known omissions.

Drift monitoring
The biggest one. A green CI gate cannot see accuracy rotting after deploy, as real-world inputs drift away from the test set.
Shadow deploys
A new model gets a copy of real traffic, logged not served, compared on real data before any canary.
Model registry
MLflow or similar — artifacts, metrics, lineage, stage labels.
Terraform
Infrastructure is a shell script that mirrors the commands actually typed. Honest, but not the real tool.
Real traffic
No users, so the canary measures its own synthetic probes. The docs say so rather than claiming "validated in production".

The loop that is built — immutable artifacts tagged by commit, a gate before deploy, a canary, one-command rollback, model version as reviewable config — is the real production shape. What changes at a larger company is the number of tools plugged into each box, not the box diagram.
